# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Build & run

Spring Boot 4.1 / Java 21 / Gradle 9 wrapper (Kotlin DSL, `build.gradle.kts`). Dependency versions come from the Spring Boot BOM via `platform(SpringBootPlugin.BOM_COORDINATES)`, so starters are declared without versions. The system `java` on this machine is a JRE only (no `javac`), so point `JAVA_HOME` at an IntelliJ-managed JDK:

```bash
export JAVA_HOME=~/.jdks/ms-21.0.12
./gradlew build                                        # compile + all tests + boot jar (build/libs)
./gradlew test --tests BatteryServiceTests             # single test class
./gradlew test --tests 'GivEnergyClientTests.readsLatestSystemData'   # single method
GIVENERGY_API_TOKEN=... ./gradlew bootRun              # run; then GET http://localhost:8082/api/battery
```

Tests need no token. `@SpringBootTest` classes must set `givenergy.poll-interval=0` and `givenergy.grid-history.sync-on-startup=false` (see `GivEnergyApplicationTests`), or the background jobs start calling the API and writing to Mongo.

The default `spring.mongodb.uri` is the real database, and there is no separate dev profile, so a local `bootRun` writes to live data unless `MONGODB_URI` is set. Stop the Docker container first when running locally: two copies don't create duplicates, but they double the API calls.

Docker: `docker compose up -d --build` builds the multi-stage `Dockerfile` (layered boot jar via `-Djarmode=tools extract --layers --launcher`, non-root JRE image) and runs it on port 8082 (`GIVENERGY_PORT` overrides the host port). The token comes from `GIVENERGY_API_TOKEN` in the git- and docker-ignored `.env`; `config/` isn't copied into the image. In the container, `localhost` in `MONGODB_URI` means the container itself.

## Architecture

Reads battery data from the **GivEnergy cloud REST API** (`https://api.givenergy.cloud/v1`, bearer-token auth), not from the inverter over the LAN.

- `GivEnergyProperties` — `givenergy.*` config (validated record). `api-token` is required and comes from `GIVENERGY_API_TOKEN` or the git-ignored `config/application.properties` (auto-loaded from the working directory); `inverter-serial` is optional (if blank, grid sync and the poller use every communication device, and range queries default to the first). `InverterDirectory` caches that list until a grid sync refreshes it, so the poller does not call `GET /communication-device` on every reading. `poll-interval` of `0` disables `BatteryPoller`. `givenergy.alerts.low-soc-percent` (default 20, `0` disables) feeds `AlertService`.
- `client/` — `GivEnergyClient` wraps `RestClient`. Every API response is wrapped in `{"data": ...}`, unwrapped via `DataEnvelope<T>`. DTO records map only the fields used; unknown JSON fields are ignored.
- `battery/` — `BatteryService` combines two calls per reading: `system-data/latest` (live SoC, battery/solar/grid/house watts, inverter status, temperature) and `meter-data/latest` (today and lifetime solar, grid import/export, house consumption, and battery charge/discharge), into a `BatteryStatus`. Exposed by `BatteryController` at `GET /api/battery`. `BatteryPoller` logs it periodically for every inverter and saves it as a `BatteryReading` in MongoDB (`spring.mongodb.uri`, default `mongodb://storenator.bluelarma.com:27017/givenergy`, collection `batteryReadings`, no auth), including the power watts. The document `_id` is `<serial>_<reading time>`, so re-polling an unchanged cloud reading upserts rather than duplicates. New power fields are nullable so older documents still load. A failed poll is recorded in memory by `AlertService` (`GET /api/alerts`); a later success clears that serial. Low SoC alerts only during the four hours after off-peak ends, and only while SoC stays below the threshold. An inverter status other than "Normal" is alerted too. Alerts are not persisted.
- `BatterySummaryJob` runs on cron `0 0 0 * * *` in `givenergy.timezone` (default `Europe/London`) and writes yesterday's per-inverter min/max SoC, peak charge/discharge watts and day's kWh to `batterySummaries` (`_id` `<serial>_<date>`, so re-runs replace). `POST /api/battery/summaries/{yyyy-MM-dd}` runs it on demand. Day boundaries are local midnight, so DST days are 23h/25h.
- Web UI: `src/main/resources/static/index.html` (served at `/`), with ARIA tabs Grid (default; export card above import), Solar and Battery state of charge. The tab choice is kept in localStorage `tab`. Charts skip rendering while their panel is hidden (zero width) and redraw from a ResizeObserver when shown. It's a single self-contained file with hand-drawn SVG candlesticks, stacked bars, a power/temperature trace and a half-hour chart, and no JS libraries or build step. It calls `GET /api/battery/candles?range=day|week|month|year` (`CandleService`): with no `anchor`, day is a rolling 24h of hourly candles from `batteryReadings`, week is 7 daily candles, month is 30, year is 365, from `batterySummaries` (needs `open`/`closeStateOfChargePercent`) plus today computed live from readings. An `anchor` date makes day that calendar day, week the 7 days ending on it, month that calendar month clipped to yesterday, and year the 12 months ending that month. `compare=true` adds the same window a year earlier (a rolling window shifts by a year; it is not turned into a calendar month). `GET /api/battery/traces?range=day|week` is the power and temperature trace (day = raw readings, week = hourly averages). Candle tooltips use `lowAt`/`highAt` and peak charge/discharge watts. CSV is `GET /api/battery/candles.csv`. Optional `?inverter=` selects one serial; the header shows a picker only when the account has more than one (`GET /api/inverters`).
- `grid/` stores daily grid history in `gridExports` (solar→grid, battery→grid; energy-flows types 2 and 6), `gridImports` (grid→home, grid→battery; types 3 and 4, plus `offPeakImportKwh`) and `energyBalances` (all seven flows, including solar→home 0, solar→battery 1 and battery→home 5). All three use `_id` `<serial>_<date>` and implement `GridDay`. `halfHourFlows` keeps the raw half-hour buckets for the last 7 local days including today (`_id` `<serial>_<start>`). `GridHistorySync` fetches **half-hourly** energy-flows (grouping 0, max 1000 buckets per call, hence `CHUNK_DAYS = 18`), sums them into local days, and splits import by `TariffProperties.isOffPeak` on each bucket's local start time.
  - It back-fills from the commissioning date when exports, the off-peak import split, or energy balances are missing. Otherwise, at startup and at 00:30 local, it re-fetches the last 2 stored days plus anything newer. The first sync after this upgrade re-fetches history because `energyBalances` is empty, and that pass stamps prices onto previously unstamped days.
  - It writes only new or changed days, and stamps `AppliedTariff` (including standing charge) the first time a day is written. A later re-fetch keeps the stored stamp even if the kWh changed. `POST /api/grid/sync[?from=date]` runs it on demand. Days that still have a null stamp are stamped with the current tariff (`stampMissing`) without a restamp endpoint, so run one sync before changing prices if history should stay at the old rate.
  - `GET /api/grid/imports|exports?range=yesterday|week|month|year` returns a generic `GridView` (parts keyed by `GridFlow.parts()`, `kwhByRate`, `amountGbp`, import-only `amountGbpByRate` rounded per rate per bar so the parts add up to `amountGbp`, `tariff`, `selfConsumptionRatio`, `selfSufficiencyRatio`, `mixedTariff`, optional `comparison`; year = 12 monthly bars). `GET /api/energy/solar|house` uses the same shape. Solar self-consumption is solar used on site / solar generation; house self-sufficiency is (solar→home + battery→home) / house load. The other ratio is null on that view.
  - Optional `anchor=yyyy-MM-dd` and `compare=true` (`RangeWindows`): with no anchor, yesterday / last 7 days / last 30 days / 12 calendar months ending yesterday. With an anchor, that day, the 7 days ending on it, that calendar month clipped to yesterday, or the 12 months ending that month. Comparison is the same window one year earlier; a rolling window is shifted by a year, not converted into a calendar month. CSV twins sit at `/exports.csv`, `/imports.csv`, `/api/energy/solar.csv` and `/house.csv`.
  - `GET /api/grid/bill` is import cost plus standing charge minus export earnings for the same window. Standing charge is one charge per calendar day in the window (from that day's import stamp, else export, else the current tariff), including days with no energy data. Default `standing-charge-pence` is 0, so existing totals stay unchanged until it is set.
  - `GET /api/grid/half-hours?days=1..7` charts the kept buckets against the off-peak window. Daily bars still end yesterday; today's kWh in the header comes from the meter counters.
  - Money is computed at read time from the day's stored `AppliedTariff` when present, otherwise from the current `givenergy.tariff.*`. Changing a price does not revalue stamped days. The off-peak *window* is stored as the kWh split, so changing it still needs `POST /api/grid/sync?from=<first date>`. The UI draws import and export on a shared y-scale.
- energy-flows quirks (verified against data-points meter counters and integrated grid power): `end_time` is exclusive. The **daily** grouping (1) is badly wrong on some BST days (e.g. 15 Jul 2026: 13.9 vs 21.1 kWh), so don't use it. Half-hourly buckets are labelled in local time and match the meter, apart from small shifts between adjacent days when the inverter clock drifts. Requests are still padded by a day either side, keeping only the inner days.
- `MongoConfig` uses the driver's java.time codecs so `LocalDate` is stored as UTC midnight. Spring Data's default uses the JVM zone, and this machine's JVM picks up Europe/London from /etc/timezone, so summer dates came out as 23:00 the day before.
- Time comes from the injected `Clock` bean (UTC), converted with `givenergy.timezone` for local days, not from `now()` or the JVM zone.
- Range queries on `time` need an explicit `@Query` (`$gte`/`$lt`): derived `...GreaterThanEqualAndTimeLessThan` fails at runtime because both criteria target the same field. Mocked repository tests won't catch this.
- `ApiExceptionHandler` maps `GivEnergyAuthenticationException` (thrown by the client on 401/403) to a 502 `ProblemDetail`.

**Sign convention:** GivEnergy reports `battery.power` as positive = discharging, negative = charging. `BatteryService.toStatus` turns that into `BatteryState` plus separate non-negative charge and discharge watt values. Grid power is positive when exporting; `toStatus` splits it into `gridExportWatts` and `gridImportWatts`.

Cloud data updates roughly every 5 minutes and the API is rate-limited, so don't poll aggressively.

Spring Boot 4 notes: Mongo connection properties are `spring.mongodb.*` (not `spring.data.mongodb.*`); starters are modular (`spring-boot-starter-webmvc`, `spring-boot-starter-restclient`, and `*-test` counterparts), and Jackson is v3 (`tools.jackson.*` packages; annotations remain `com.fasterxml.jackson.annotation`).
